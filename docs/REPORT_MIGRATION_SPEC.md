# RiskPilot 报告板块迁移清单

## 1. 产品不是一个页面，而是两条完整路径

RiskPilot V2 必须同时保留下面两条路径，任何一条缺失都不能称为完整迁移：

| 路径 | 用户目的 | 当前 V2 状态 |
|---|---|---|
| 股票风险分析与报告 | 输入本金和最大损失，理解历史样本、风险预算和多视角证据 | 底层能力部分完成，完整报告尚未迁移 |
| 时间穿越挑战 | 在未知后续行情时连续决策，检验风险纪律并参与排行榜 | 核心后端、持久化、审计和 HTTP API 基本完成 |

两条路径有关联但不能混为一体：用户可以独立进入挑战，也可以在完成报告后带着同一股票进入挑战。报告不能读取挑战未来节点，挑战也不能把后续行情倒灌进报告。

## 2. V1 报告链路盘点

当前 V1 的 `/api/analyze` 一次完成了过多职责：

```text
股票、本金、最大损失
  → 读取本地股票快照
  → 提取价格、ATR、支撑位、均线、RSI和目标参考位
  → 技术面 Agent
  → 基本面 Agent
  → 信息面 Agent
  → 确定性资金面分析
  → 确定性风险计算
  → 历史价格触及检验
  → 生成操作计划和市场趋势说明
  → 组装结构化报告
  → 计算 SHA-256
  → 转换 Markdown
  → 放入进程内缓存
  → 返回报告、Markdown和K线数据
```

页面实际展示 11 组内容：

1. 分析结论和大白话摘要；
2. 股数、止损、损失预算和风险收益比；
3. K 线、均线和关键价位；
4. 压力测试；
5. 历史价格触及检验；
6. 历史情景操作计划；
7. 同板块观察；
8. 技术面、基本面、信息面、资金面四个视角；
9. 数据来源和证据包；
10. 风险计算与费用明细；
11. 报告哈希验证、Markdown 下载和进入历史挑战的入口。

这里的“四个视角”并不等于四次模型调用：技术面、基本面和信息面目前可调用模型；资金面由 OHLCV 数据确定性计算。

## 3. 已完成与缺失能力

| 能力 | 状态 | 说明 |
|---|---|---|
| 风险预算计算 | 已完成 | `calculate_risk_budget` 已有新旧一致性测试 |
| 历史快照和哈希 | 已完成 | 已有时间边界与篡改检测 |
| 从快照提取风险输入 | 已完成 | 当前只覆盖风险计算所需字段 |
| 统一模型接口 | 已完成基础 | 已有 `ModelGateway` 和明确离线模式，尚未迁移三个 Agent |
| 资金面确定性计算 | 尚未迁移 | 仍位于 V1 `backend/capital_flow.py` |
| 历史触及检验 | 尚未迁移 | 仍与 V1 API 编排耦合 |
| 趋势和情景计划 | 尚未迁移 | 仍在 V1 API 中临时组装 |
| 四视角输出 | 尚未迁移完整 | 三个 Agent 仍走 V1，资金面仍是 V1 模块 |
| 报告组装与 Markdown | 尚未迁移 | 仍依赖 V1 数据类型和模块路径 |
| 报告持久化 | 未完成 | V1 只按股票代码放在进程内缓存，重启丢失且没有用户隔离 |
| 报告查询与校验工具 | 未完成 | V2 Harness 尚无对应工具 |
| V2 报告 HTTP API | 未完成 | 当前 `/api/v2` 主要覆盖挑战路径 |
| 小程序报告页面 | 未开始 | 必须等报告契约稳定后再制作 |

## 4. 当前数据的真实边界

仓库目前有 100 只股票池以及 102 份分析快照。多数扩展样本包含 161 个交易日的 OHLCV，但没有新闻、公告或完整基本面资料；只有少数演示样本包含更丰富信息，其中还有明确标记的合成数据。

因此 V2 必须遵守：

- 有价格和成交量时，可以生成风险、技术指标和资金面历史观察；
- 没有财务数据时，基本面必须显示“证据不足”，不能补写公司经营结论；
- 没有公告新闻时，信息面必须显示“证据不足”，不能靠模型常识补写；
- 合成样本必须在报告顶部和相关模块持续标识；
- `as_of` 之后的文件、行情和事件不能进入报告；
- 数据许可仍为 `review_required`，公开分发前必须完成授权核验。

## 5. 迁移时必须修正的 V1 风险

1. V1 报告缓存只以股票代码为键，不区分用户，也会在服务重启后丢失。
2. V1 的 `/api/report/{stock_code}` 不适合作为 V2 用户报告查询方式。
3. “怎么买”“怎么卖”“目标价”“可以考虑买入”等措辞不适合直接进入公众小程序，应改成历史风险教育和情景观察表达。
4. 模型输出目前以长文本为主，失效条件还依赖字符串查找，应改成版本化结构字段。
5. 不能把预设文案标记成当次真实 AI 推理；离线和证据不足必须明确可见。
6. 报告哈希只能证明同一份内容有没有变化，不能证明数据正确、模型正确或具有第三方时间见证。
7. 报告生成、模型调用、确定性计算和缓存集中在一个接口函数中，难以单独测试和替换。

## 6. V2 目标调用链

```text
报告请求（用户、股票、本金、最大损失、as_of）
  → Harness 场景与身份策略
  → 校验证据并取得可见快照
  → 确定性提取价格、风险、趋势、资金面和历史触及指标
  → 有证据时才调用技术面 / 基本面 / 信息面解释器
  → 确定性组装报告并计算最终哈希
  → 以 report_id + user_id 写入 SQLite
  → 返回报告摘要、完整结构、图表数据和 Markdown
  → 用户可选择进入同一股票的历史挑战
```

模型失败不能改变风险数字，也不能让已经完成的确定性报告整体消失。报告应保留可用的确定性部分，并明确标记哪些解释不可用。

## 7. 分步实施清单

### R0：报告基线

- [x] 为真实样本、合成样本、证据不足样本和风险否决样本建立固定报告夹具。
- [x] 记录 V1 的关键数字、报告字段、Markdown和哈希行为。
- [x] 明确哪些字段要求完全一致，哪些文案需要为公众版改写。

R0 对照规则：风险预算、股数、止损距离、费用、标准情景损失和压力测试等确定性数字必须保持一致；报告字段只能通过显式版本升级调整。面向公众的“买入、卖出、目标价、操作建议”等措辞不作为兼容目标，必须在 R1 改写成历史情景与风险纪律表述。生成时间和最终哈希随报告内容变化，不要求固定为同一个字符串，但哈希验证行为必须一致。

### R1：确定性报告领域层

- [x] 迁移资金面指标为纯领域函数。
- [x] 迁移历史价格触及检验和趋势判断。
- [x] 将“目标价”改成清楚标识的“历史情景参考位”。
- [x] 将“买卖操作计划”改成“风险纪律检查清单”。
- [x] 创建版本化、结构化的确定性报告模型。
- [x] 保证同样的快照、输入和规则版本产生同样的数字。

R1 的实现位于 `src/riskpilot/domain/reporting.py`。它不读取数据库、不调用模型、
不读取系统时间，也不依赖 HTTP 请求。资金面中的“流入/流出”仅是根据上涨日与
下跌日成交量形成的历史方向估算，不代表真实主力资金数据。V1 的旧接口仍暂时保留，
直到 R3 使用新的报告组装工具替换它。

### R2：多视角解释层

- [x] 将技术面、基本面和信息面拆成三个独立解释器。
- [x] 资金面保持确定性计算，不伪装成模型 Agent。
- [x] 为每个解释器定义结构化输出、提示词版本和证据引用。
- [x] 证据缺失时返回明确的 `insufficient_evidence`。
- [x] 模型离线或失败时保留确定性报告并显示降级状态。

R2 的三个解释器位于 `src/riskpilot/agents/report_perspectives.py`，通过统一
`ModelGateway` 注入模型。模型只返回独立的结构化解释，不能覆盖 R1 的确定性结果；
未知证据引用、非 JSON 输出和公众版禁用交易措辞都会被拒绝。离线状态不使用预设
文案冒充模型结果。V1 的三个 Agent 仍作为旧页面兼容代码保留，R3 组装新报告时才
正式切换到这些解释器。

### R3：报告生成与持久化

- [ ] 创建确定性 `build_risk_report` 工具。
- [ ] 创建 `get_risk_report` 和 `verify_report_integrity` 工具。
- [ ] 使用 `report_id`、内部 `user_id`、`snapshot_id` 和版本信息保存 SQLite 报告。
- [ ] 保存最终结构化报告和 Markdown，不使用仅按股票代码的进程内缓存。
- [ ] 增加跨用户读取、内容篡改、重复请求和重启恢复测试。

### R4：报告 HTTP API

- [ ] `POST /api/v2/reports`：生成报告。
- [ ] `POST /api/v2/reports/query`：读取当前用户的一份报告。
- [ ] `POST /api/v2/reports/integrity`：验证报告哈希。
- [ ] `POST /api/v2/reports/list`：查询当前用户的报告历史。
- [ ] 返回小程序绘图所需的时间隔离 OHLCV，不返回未来数据。
- [ ] 跑通“生成报告 → 查询 → 校验 → 下载 → 带同一股票进入挑战”。

### R5：界面与小程序

- [ ] 先确定双入口：首页明确展示“风险报告”和“时间穿越挑战”。
- [ ] 根据手机屏幕重新排序报告内容，不照搬桌面网页的 11 张长卡片。
- [ ] 完成两个板块的低保真交互流程后，再做颜色、动效和品牌视觉。
- [ ] 报告与挑战都通过 V2 API，不调用 V1 `/api/analyze`。

## 8. 开始实现前需要产品确认的事项

以下内容会改变用户体验，不应由代码自动替用户决定：

1. 小程序首页是并列展示两个板块，还是先进入报告、再引导进入挑战；建议并列展示，同时保留报告完成后的挑战入口。
2. 是否保留技术面、基本面、信息面、资金面四个视角；建议保留，但证据不足时不生成结论。
3. 是否接受将“目标价、怎么买、怎么卖、可以买入”等措辞统一改为“历史情景参考位、风险纪律检查、模拟观察”。建议修改。
4. 首版报告是否只开放证据较完整的少量样本，还是开放 100 只并对缺失模块明确显示证据不足。建议先开放证据完整样本，再逐步扩充。

## 9. 报告板块完成标准

只有同时满足以下条件，才进入微信登录和小程序正式接入：

- 两条产品路径都能通过 V2 Harness 和 `/api/v2` 完整运行；
- 报告数字来自确定性规则，模型只能解释；
- 报告有用户隔离、持久化、版本、快照、哈希和审计记录；
- 证据不足、模型离线、模型失败和数据篡改路径都有自动化测试；
- V1 与 V2 的关键数字对照通过；
- 公众版措辞和数据授权边界已经确认。
